# First safe upload: publication engine

Task 8 publication/recovery API, 2026-10-16 (revised for the desktop reviewed-upload/recovery integration, explicit repository bootstrap and the later Resolve replacement push). `CollectionUploader` in Remote implements an explicit initial-upload operation, explicit user-confirmed repository initialization/adoption and a reviewed `ReplaceManaged` mode that replaces the managed namespace while preserving unrelated entries; see [resolve differences](resolve-differences.md). The desktop drives it through an explicit reviewed-upload journey. Successful-sync persistence stores the pinned remote revision, verified collection fingerprint and local/remote pairing in a versioned local store following existing store conventions. After a successful upload, the sync state is persisted so the recovery notes (intent/candidate/receipt records) and the "last uploaded" note (`local-sync-state.json`) match. Publication is never reported as synchronization success. No live GitHub writes were performed during implementation. The three bootstrap cases are specified in [repository bootstrap](repository-bootstrap.md).

## Supported operation and authorization

`UploadAsync(UploadRequest, cancellationToken)` requires an explicit request containing operation ID, exact canonical source root, reviewed collection fingerprint, numeric repository identity/full name/default branch and reviewed pinned commit (empty for the unborn case), plus the reviewed `RepositoryBootstrapCase`. A task-7 `PreparedOperation` alone cannot trigger publication. The store reconstructs the complete inventory and final preparation journal from disk; caller-supplied snapshot paths or file inventories are never trusted.

The supported directions are a populated local capture into an **already managed, verified empty collection at a real commit** (`Bootstrap.None`), or an explicit reviewed bootstrap selected by the cloud classification: an **unborn** repository (the manifest is seeded through the Contents API to create the first commit and default branch, then a child commit adds the complete collection), an **empty tree** at a real pinned commit (child commit, non-forced PATCH), or an **unrelated** populated repository (child commit preserving every unrelated entry verbatim, only after an explicit adoption acknowledgement). All require no existing successful-sync state and no retained evidence. The backend independently revalidates private/nonarchived/enabled repository identity, installation Contents write/user push permission, branch reference and managed bytes, and requires the exact reviewed classification/head. Populated managed collections, incompatible managed data, mismatched classifications, empty local inventories and any existing `local-sync-state.json` are blocked. There is no implicit initialization/adoption, reconciliation/removal policy or baseline bypass.

## Coordination and immutable bytes

Remote now references Local as well as GitHub/Core. Local still has no GitHub dependency, and GitHub has no Core/Local dependency. Internal friend-assembly capabilities expose scoped operations only to Remote. The public scanner and file inclusion rules are unchanged.

The complete upload or assessment holds the existing per-application-storage semaphore and exclusive filesystem lease. Preparation and other recovery/upload instances cannot interleave. It also holds the single composed `GitHubConnection` credential/selection gate, excluding selection, refresh and disconnect until the operation ends. Lock order is local storage, then connection; these services never acquire in reverse order. Cancelled waiters cannot release another operation's gate. Existing unrelated/partial recovery evidence blocks publication. Credential rotation remains per connection instance; use one app instance per account/client and one application-storage location. There is no new global cross-process credential protocol.

The operation rehashes both complete snapshots and the current source under the lease. Every uploaded payload is bounded-read through the regular-file/no-follow reader and independently compared with the saved size and SHA-256. All privately owned payload arrays and the generated manifest/tree pass a complete task-6 round-trip verification before any Git object POST. Source/capture/backup are revalidated before intent and again after candidate recording, before publication. The entire transfer uses retained captured bytes; it never rereads live source bytes for upload. Task-6 limits apply, including the manifest/aggregate/whole-tree limits. Oversize inventories block wholly; generic inspection gains no exclusions.

Local files are never replaced. Application storage is not an OS-enforced immutable volume and the lease cannot lock external writers. Task-7 ancestor-replacement and filesystem durability limitations still apply. A source edit detected after publication produces `PublishedSourceChanged`; current user bytes are retained and no baseline is written.

## Durable publication protocol

The existing preparation inventory and chained journal remain schema 1 and unchanged. A new `upload/` directory in the retained operation contains up to three create-new, bounded (16 KiB) schema-1 JSON records:

| Record | Exact binding and boundary |
|---|---|
| `intent.json` | Direction (`Upload`/`Initialize`/`Bootstrap`/`Adopt`), operation ID/root/fingerprint, SHA-256 of final preparation record (transitively binding the complete inventory/chain), repository ID/full name/branch, pinned parent and original root tree (`Initialize` binds null parent/tree); flushed before object creation |
| `candidate.json` | Direction, SHA-256 of exact intent bytes, verified candidate commit and root tree; flushed before any branch update |
| `published.json` | SHA-256 of exact candidate record bytes and candidate commit; written only after a fresh pinned cloud read verifies the exact candidate tree and complete collection at the current head |

All use task-7 create-new temporary-write, file flush, rename and parent-directory durability. Records are never overwritten or removed. Unknown, duplicate, missing, malformed, future, oversized, linked, out-of-sequence or mismatched records fail closed. Temporary files and an empty/interrupted upload directory require review, never authorization. Hashes provide consistency, not protection from an attacker able to rewrite all app-owned evidence. Generic local `AssessRecoveryAsync` returns Blocked with guidance to use publication assessment when an upload directory exists; it cannot report Prepared and accidentally conceal remote-write evidence.

Publication creates bounded base64 blobs, explicit direct-child Git trees and one commit with the observed head as its **single parent**. Returned blob/tree IDs are checked against locally computed Git object IDs; the immutable commit is fetched to confirm its tree and sole parent. Unrelated root entries and all their referenced subtrees/modes/IDs are preserved verbatim; no `base_tree`, deletion entry or replacement of unrelated content is used. The generated complete tree must still fit the reader limits.

Immediately before reference update, fresh repository/access/head checks must match the pinned original commit/tree (or the unborn seed commit), and local evidence is revalidated. For the unborn case the default branch is created by the Contents API seed; the only reference update is one non-forced PATCH of the branch. There is no forced update, automatic retry, reparenting or automatic merge. GitHub's REST update enforces fast-forward, not an atomic expected-old-SHA compare-and-swap. Concurrent normal advances reject the sibling candidate; an external history rewind racing the final check cannot be excluded by this API. No branch lock or stronger remote transaction guarantee is claimed.

Protocol references: GitHub's [blob creation](https://docs.github.com/en/rest/git/blobs#create-a-blob), [tree creation](https://docs.github.com/en/rest/git/trees#create-a-tree), [commit creation](https://docs.github.com/en/rest/git/commits#create-a-commit) and [non-forced reference update](https://docs.github.com/en/rest/git/refs#update-a-reference).

## Lost responses and restart

Any transport error, cancellation or interruption retains evidence. Do not call Upload again: the existence of upload evidence blocks replay. `CollectionUploader.AssessRecoveryAsync(operationId, repository)` acquires the same gates, validates the complete record chain and exact repository pairing, and performs only remote reads. It may append a verified local publication receipt; it never creates remote objects or updates references.

| Result | Meaning |
|---|---|
| Interrupted | Valid intent exists without a candidate; no reference update could have been attempted. Unreachable Git objects may exist. Review retained evidence. |
| NotPublished | The current verified head is still the pinned parent and no receipt exists. This is an observation, not proof that publication never happened before a rewind. No automatic retry is authorized. |
| ConcurrentUpdate | Current head differs from parent/candidate, or returned to parent after a receipt. Preserve candidate and refresh/review. Even a descendant is unresolved without ancestry evidence. |
| Published | Fresh managed-byte verification finds the exact candidate at the current head, complete snapshots/current source still verify, and a durable receipt exists. This confirms publication only. |
| PublishedSourceChanged | Exact candidate publication verifies, but current source differs or cannot be verified. Preserve the edit and backup. No synchronization success is claimed. |

Corrupt or unavailable evidence/access raises a blocking exception; it never becomes empty remote state. A new branch head after a lost response remains unresolved even if it happens to contain identical files. No ancestry or successful baseline is fabricated. Repeated assessment for unchanged inputs is idempotent. Captures, backups, journals, orphan objects and publication records remain retained; reviewed cleanup/abandonment and ordinary subsequent uploads are not implemented.

## Desktop reviewed upload and recovery

`SyncViewModel` in Desktop composes the child inspection/cloud/connection view models with an `IUploadOperations` seam (`SyncOperations` for production). `SyncOperations` shares one application directory between the preparation store, the sync-state store and the uploader, and reuses the single composed `GitHubConnection` for the credential/selection gate; the desktop itself never writes source files, evidence or remote objects.

- **Offer gate.** `Sync All` (labelled by bootstrap case) is enabled only when the local inspection is valid and populated, no `local-sync-state.json` baseline exists and no retained recovery evidence exists, and the cloud check returned either a verified empty managed collection at a real pinned commit (advisory comparison `InitialUpload`) or an explicit bootstrap case (unborn, empty tree or unrelated). The dashboard always shows the reason it is unavailable; incompatible managed data keeps it disabled.
- **Baseline ancestry.** Before an existing baseline is trusted, `CollectionUploader.VerifyBaselineAncestryAsync` checks the saved commit is an ancestor of the current remote head. A non-ancestor baseline is reported as "no longer part of the remote history" and never offered for upload or treated as a valid synchronization state. An ancestor baseline still does not enable a second upload (subsequent uploads are unimplemented).
- **Review.** `Sync All` opens an explicit review naming the bootstrap case (or the ordinary initial upload) and showing the exact repository, branch, pinned revision, file list, count, byte total and fingerprint. Confirm stays enabled only while every reviewed input (local fingerprint/root, selected repository/branch, cloud revision and classification) is unchanged. The unrelated (adoption) case additionally requires an explicit acknowledgement. Any change underneath drops the prompt and requires a fresh review. The backend then prepares and publishes under its own gates; it never rereads live source bytes.
- **Result.** The screen reports exactly what happened: `Published` (publication only, explicitly "not a verified two-device synchronization"), `PublishedSourceChanged`, `NotPublished`, `ConcurrentUpdate`, `Interrupted`, `Blocked` or cancelled. Never "Synced".
- **Recovery.** A separate read-only `Upload Recovery` screen lists retained publication evidence, assesses it under the exact repository pairing, and reports `Published`/`PublishedSourceChanged`/`NotPublished`/`ConcurrentUpdate`/`Interrupted` without re-uploading, replacing files or writing a baseline. Re-checking is idempotent. A repository/pairing mismatch blocks instead of reusing evidence.
- **No background sync.** Only the explicit confirm runs prepare/upload. Startup, selection and Refresh remain read-only except that they load the baseline (verifying ancestry) and list retained evidence.
